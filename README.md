A library of low-poly 3D models that are **generated by Python scripts running in Blender**, not modelled by hand: change a number, rebuild, get a new model. One shared 16 x 16 colour palette, flat shading, no textures to author. It began as the art pipeline of a co-op game and is being split out so anyone can use it.

Status: **extraction in progress.** The scripts under `art/` are a copy of the game repo's `art/` folder (from its `main`, 2026-10-23); the generic library and the game-specific content are not separated yet. See [NOTES.md](NOTES.md). There is a browsable [asset browser](#the-asset-browser) for a first slice of 303 models.

AI disclosure: the Python scripts were written with the help of Claude Code (Anthropic). The models themselves are not made by a text-to-3D or image generator: each one is built by a script from boxes, cylinders and lofted cross-sections, and you can read how.

What it can make today (the file list is in [art/README.md](art/README.md)): quadruped animals from a description (any species, dog breeds, cat coats), people on a shared humanoid rig with clips, road vehicles in paint jobs and New / Damaged variants, furniture, appliances with doors and drawers that open, a modular building kit, vegetation, ships, produce in several colours, insects, sports gear (balls, goals and nets, bats, rackets, a helmet) and office gear (desks, a cubicle kit on a 1.5 m module, a copier, a water cooler).

## How a model is made

1. **A script describes it.** Each file in `art/scripts/` builds a family of models: `cars.py` (sedan, taxi, ambulance, tractor...), `interactive.py` (a fridge, a wardrobe: their doors and drawers are separate parts), `gn_animals.py` (animals from a species table), `gp_cast.py` (people), `kit.py` (walls, doors, roofs on a 3 m grid)... A prop is a few lines of boxes, cylinders and lofted cross-sections from `props_lib.py`:

   ```python
   p = Prop("GT_Barrel_01")
   p.cyl("wood_dark", (0, 0, 0.45), 0.28, 0.9, n=10)       # colour, centre, radius, height
   p.box("metal_dark", (0, 0, 0.2), (0.6, 0.6, 0.04))      # colour, centre, size
   obj, coll = p.finish()                                  # one mesh, one material, origin on the floor
   common.export_fbx(coll, "Assets/Art/Global/Props/GT_Barrel_01.fbx")
   ```

2. **Colours come from one palette**, `common.PALETTE`: 256 slots in a 16 x 16 grid, each swatch 4 x 4 pixels of the 64 x 64 texture `GlobalPalette.png`. A script names a colour (`"wood_dark"`), never an RGB value; every UV of a face points at the middle of one swatch, so a model needs no unwrapping and a variant is a colour remap. The palette is **append-only**: indices are baked into the UVs of every exported model. A few swatches glow (`glow_cyan`, `glow_green`, `glow_red`, `glow_amber`): they are ordinary colours in the texture, and an engine can light them up with an emissive mask (the asset browser does).
3. **Flat shading.** Every model is faceted: hard edges, no smoothing groups, no subdivision (about 60 to 700 triangles for a prop or a vehicle, 500 to 1,000 for an animal or a person). The exported normals are per face.
4. **Variants are data, not copies.** Modern / Retro / Damaged furniture, paint jobs, building skins and Rotten food are one definition with a colour remap and, where the shape differs, its own function (`art/README.md`, "Variants").
5. **Conventions** (units, axes, origin): see [Using the models in your engine](#using-the-models-in-your-engine). Details of the pipeline, the checks (`audit.py`, `audit_props.py`) and the traps: `art/README.md`.

## Categories and tags

Every model in the browser has one **type**, a three-level lowercase path, `category/group/kind`, for example `vehicles/road/sedan`, `furniture/seating/sofa`, `appliances/kitchen/fridge`. The top-level categories in the first slice are `vehicles`, `animals`, `people`, `furniture`, `appliances`, `decor`, `food`, `farm`, `building`, `nature`, `sports`, `fixtures` and `equipment`. It also has many **tags** (lowercase words): the setting (`modern`, `retro`, `classic`, `rural`, `urban`, `suburban`, `sci-fi`, `diner`), the condition (`new`, `damaged`, `rotten`, `abandoned`, `fresh`, `weathered`), colours (`red`, `blue`...) and anything that helps a search (`kitchen`, `emergency`, `livestock`...). Models that are the same shape in another skin, style or colour are listed as each other's **variants**. The table that holds all this is `tools/catalog.py`; the rules for it are tested (`tests/test_catalog.py`).

## The asset browser

`site/` is a static page (no build step, no framework; three.js is vendored under `site/vendor/three`, MIT) that browses 303 of the models: search as you type, a category tree, tag chips that filter together, a thumbnail grid and a 3D viewer with orbit / zoom / pan, a variant switcher, doors / drawers / lids you click to open (and an "Open all" button) and, for animals and people, a clip dropdown (Idle, Walk, Trot, Run, Sit) with a speed slider. `#GV_Sedan_01` in the URL opens a model; the filters are in the query string. It works at phone width.

Run it locally:

```bash
cd site
python -m http.server 8000      # then open http://localhost:8000
```

It has to be served over http (a `file://` page cannot load the models). Publishing: `.github/workflows/pages.yml` deploys `site/` with GitHub Pages to https://khanjal.github.io/lowpoly-assets/ when a change to `site/` reaches `main` (the repository is public, which Pages needs on the Free plan).

**Downloading.** The viewer's *Download GLB* button gives one model. [Releases](https://github.com/khanjal/lowpoly-assets/releases) have zips of every GLB and of each category (`lowpoly-assets-glb-all.zip`, `-vehicles.zip`...), made by `.github/workflows/release.yml` when a `v*` tag is pushed (or by hand from the Actions tab); `python tools/make_release_zips.py` makes the same zips locally into `dist/`. Each zip has `CREDIT.txt` and `LICENSE-MODELS`, and every GLB carries the credit line in its `asset.copyright` field. FBX files are not published (they are not committed; building them needs Blender).

`site/manifest.json` describes every model, one entry each:

| Field | Meaning |
|---|---|
| `id`, `name` | the model's file name without extension (`GV_Sedan_01`), a display name |
| `aliases` | ids the model had before (`GV_Sedan_Blue_01`): old links and searches still find it |
| `type`, `tags` | one category path; many tags |
| `rigged`, `interactive` | has a skeleton; has moving parts |
| `triangles`, `size` | triangle count; `[width, height, depth]` in metres |
| `glb`, `thumb` | paths under `site/` |
| `parts` | moving parts: `kind` (`hinge`, `slide`, or `spin` for a wheel that turns freely about its axis; its `limit` is 360), `axis` (a unit vector), `pivot`, `limit` (degrees to open, or metres to slide; the sign is the direction), `rest` (how far open the exported pose is; 0 = shut), **in glTF axes** |
| `clips` | animation names in the GLB |
| `variants` | ids of the same model in another skin |

## Rebuilding the assets

The scripts run inside Blender (5.2.3 here) through the Blender MCP add-on, which runs `execute_blender_code`:

```python
import runpy
runpy.run_path(r"<repo>\art\scripts\gt_bucket.py", run_name="__main__")      # always pass run_name: most scripts build only under __main__
```

Options go in `init_globals` (for example `{"SPECIES_LIST": ["goat"]}`). Exports are written under an **output folder**: `out/` by default, set with `common.configure(out=r"<folder>")` or the `LOWPOLY_OUT` environment variable (a path such as `Assets/Art/Global/Props/GT_Bucket_01.fbx` is relative to it, so pointing it at a Unity project's root gives the old behaviour). `common.configure(formats="fbx,glb")` also writes GLB files (`common.export_glb`), `only={...}` limits the exporters to some names, and `prefix=` keeps a build from replacing same-named collections in a Blender file that other work shares.

To rebuild the browser's slice:

| Step | Command |
|---|---|
| models | in Blender: `runpy.run_path(r"<repo>\tools\build_site_assets.py", init_globals={"GROUPS": ["cars_sedan"]}, run_name="__main__")`, one group per call (see `tools/catalog.py` for the group names; run `people`, `animals` and `birds` on their own, they take about 20 seconds each) |
| manifest | `python tools/make_manifest.py` |
| thumbnails | `python tools/thumb_server.py`, then open `http://localhost:8766/tools/thumbs.html` in a browser (it renders every model with the site's own viewer and saves `site/thumbs/<id>.png`; `?only=ID,ID` for some) |
| credit line | `python tools/stamp_glb.py` (writes the CC BY 4.0 credit into `asset.copyright` of every `site/models/*.glb` that lacks it; Blender's exporter does it for new builds, `check_site.py` fails without it) |
| check | `python tools/check_site.py` |

## Using the models in your engine

**What is checked and what is not.** The models have been looked at in three.js (this site) and, for the FBX files, imported in Unity in the game repo (per `art/README.md`, "Unity import checklist"). Nothing here has been imported into Godot or Unreal, and the GLB files have not been imported into Unity. The table and the notes below separate what an engine's own documentation says (with the page) from what has been tried.

| Engine | Format | Status |
|---|---|---|
| three.js (this site's viewer) | GLB | **tested**: loads, textures nearest-filtered, clips play, moving parts turn about the right pivots |
| Blender 5.2.3 | generation, GLB and FBX export | **tested** |
| Unity | FBX | **tested in the game repo** (palette Point-filtered, People as Humanoid, models arrive facing +Z); not re-tested for this repo |
| Unity | GLB | **documented**: needs the glTFast package; **untested** |
| Godot 4.x | GLB (glTF 2.0) | **documented** (the recommended format; its asset front is +Z, which is where glTF puts the front); **untested** |
| Godot 4.x | FBX | **documented** (imported with ufbx from 4.3); **untested** |
| Unreal Engine 5 | FBX | **documented** (import options); **untested** |
| Unreal Engine 5 | GLB | **documented** (Interchange framework); **untested** |

### Formats

- **FBX** (`art/scripts/common.py`, `export_fbx`): `-Z` forward, `Y` up, scale 1, flat (face) normals, no leaf bones. Static meshes are exported with the axis conversion baked in; **rigged ones are not** (baking rotates the bones), so the importer has to apply the conversion (in Unity, "Bake Axis Conversion"). Rigged models are in a T-pose; their clips are separate FBX files named `Model@Clip.fbx` (Unity names the clip from the `@`), except the Insectoid, whose clips are inside its file.
- **GLB** (`common.export_glb`, what the site uses): binary glTF 2.0, Y up, metres, per-face normals, the palette as an embedded 64 x 64 PNG with a nearest-neighbour sampler. A rig's clips are animations (the site's people have `Idle`, `Walk`, `Run`, `Sit`; dogs `Idle`, `Walk`, `Trot`, `Run`), sampled at 60 fps. A moving part is its own node with its origin on the pivot. Only meshes and armatures are exported: the marker empties (below) are **not** in the GLBs.

### Units, axes and facing

- 1 unit = 1 metre. Origin on the floor at the middle of the base; wall pieces have it at the middle of the mount.
- In Blender and in the scripts: **+Z up, the model faces −Y** (its front is at −Y, its back at +Y), +X is the character's left.
- In glTF the exporter turns Blender's (x, y, z) into (x, z, −y): **+Y up, the front faces +Z** (the glTF 2.0 spec, section 3.4, "Coordinate System and Units": right-handed, +Y up, the front of an asset faces +Z). So a model's front is at +Z in a GLB.
- **Unity** (FBX): the game repo's notes say a model faces −Y in Blender and arrives facing +Z in Unity, which is Unity's forward; static meshes need nothing, rigged ones need "Bake Axis Conversion" if they come in with a stray 90° rotation (`art/README.md`, "Axes"). The FBX importer's options (Scale Factor, Convert Units, Bake Axis Conversion, Normals: Import) are described at `docs.unity3d.com/Manual/FBXImporter-Model.html`.
- **Godot 4.x**: right-handed, Y up, 1 unit = 1 m (`docs.godotengine.org`, "Introduction to 3D"). Godot's camera and nodes look down −Z, but its convention for **assets** is the opposite: the "Model export considerations" page says the +Z axis is the front of an asset and −Z its rear, and that for Blender +Y is the rear and −Y the front; `Vector3.MODEL_FRONT` is (0, 0, 1) and `FORWARD` is (0, 0, −1) (class reference). So **a glTF model with its front at +Z should import facing the right way, with no turn about Y** (documented, not tried here). The belief that glTF models come in backwards in Godot because Godot's *forward* is −Z mixes up the node forward with the asset front. Use `look_at(..., use_model_front = true)` to turn an asset towards a target. (How the FBX importer orients a file: not tested.)
- **Unreal**: the FBX import options "Convert Scene" and "Force Front XAxis" convert from the FBX coordinate system to Unreal's; the second uses X instead of −Y as the front axis (`dev.epicgames.com`, "FBX Import Options Reference"). Unreal's units are centimetres (general knowledge, not from the pages I read): scale a model in metres by 100 ("Import Uniform Scale"). **Facing in Unreal has not been checked**: expect to import one model and set the options once.

### The palette texture: nearest-neighbour, no mipmaps

All models share one texture, 64 x 64 pixels, 16 x 16 swatches of 4 x 4 pixels. **Sample it with nearest-neighbour filtering and no mipmaps**, or the colours of neighbouring swatches blend (stripes on walls at a distance). In the GLBs the sampler already says `NEAREST` for magnification, but its minification filter is `NEAREST_MIPMAP_NEAREST`, so an engine that generates mipmaps can still smear the swatches at a distance: turn mipmap generation off. In Unity the game repo does this in `ArtImportRules` (Point filter, no mipmaps, no compression). In Godot it is the material's texture filter ("Nearest") and the texture's mipmap import setting; in Unreal the texture's filter and mip settings (both from general knowledge of those engines, not checked against their docs).

Every FBX references a material called `GlobalPalette`; use one shared material for all models, with low smoothness / roughness and no metallic. To make the glowing swatches glow, build a second texture holding only the glow swatches' pixels (the browser does it: `site/viewer.js`, `_glowMap`; the swatch indices are in `site/manifest.json`, `palette.glow`) and use it as the emissive map.

### Flat shading

The normals are per face and are in the files. Import them as they are: Unity "Normals: Import" (the default, per the manual) and Unreal "Import Normals" (not "Compute Normals", which discards the file's smoothing and normal information, per its options reference). Godot: leave the normals alone (not checked). Do not recalculate or smooth them, or the facets disappear.

### The humanoid skeleton and clips

People share one rig: **65 bones**, the layout of Quaternius's Universal Animation Library (CC0), listed with head and tail positions in `art/data/ual_skeleton.json`: `root`, `pelvis`, `spine_01`..`spine_03`, `neck_01`, `Head`, then for each side `clavicle_`, `upperarm_`, `lowerarm_`, `hand_`, four-joint fingers and a thumb, and `thigh_`, `calf_`, `foot_`, `ball_` (suffix `_l` or `_r`). The rest pose is a **T-pose**, facing −Y in Blender (+Z in glTF). The clips (`Idle`, `Walk`, `Run`, `Sit`, `Carry`, `CarryOne` as FBX; the first four are in the GLBs) are in place, with no root motion, and play on every person because they share the skeleton.

- **Unity**: set the rig to **Humanoid** (Create From This Model); the game repo reports that every person maps cleanly. The Avatar system is what lets one humanoid's clips play on another (`docs.unity3d.com/Manual/AvatarCreationandSetup.html`; the page I could read did not state a T-pose requirement).
- **Godot 4.x**: in the advanced import dialog set a `BoneMap` with the `SkeletonProfileHumanoid` profile; Godot auto-maps by name patterns and recommends common English bone names; the profile's reference pose is a T-pose facing +Z, which is how these models arrive (`docs.godotengine.org`, "Retargeting 3D skeletons"). The Retarget import options let clips from one model play on another. Untested here.
- **Unreal**: create an IK Rig for the source and the target, define the retarget chains, and an IK Retargeter between them; match the retarget poses when the reference poses differ (`dev.epicgames.com`, "IK Rig Animation Retargeting"). Untested here.
- Animals use a different, quadruped skeleton (`art/scripts/quadruped_rig.py`) with its own Idle / Walk (dogs also Trot / Run) clips; birds have a biped-bird rig and no clips yet. They are Generic rigs.

### Marker empties and `interactions.json`

Besides the mesh, an FBX can carry **empties** that mark places, and `art/data/interactions.json` describes what can be done with each model:

- `Socket_Front` and `Socket_Back`: just outside the front and back faces (every FBX has them): line `Socket_Back` up with a wall, stand a character or open a door at `Socket_Front`.
- `Slot_<name>`: where loose items go (a fridge shelf, a drawer floor); a slot that rides on a part moves with it.
- `Light_<name>`, `Sound_<name>`, `Switch_<name>`: a lamp's bulb, a fridge's hum, a switch; the JSON says what each does (colour, range, which clip, who may use it).
- `parts` in the JSON: the moving parts (`kind`, `axis`, `pivot`, `limit`, `rest`) **in Blender's axes**. The browser's manifest has the same parts already converted to glTF axes.

**These are data.** Nothing plays or lights by itself: each engine needs a small importer that reads the empties and the JSON and builds its own lights, audio sources, hinges and slides. `art/README.md` describes Unity code that does this in the game (`PropRuntimeSetup.cs`, `PropRuntime.cs`), but that code is not in this repo and it has not been checked here whether it is on the game's `main`. The empties are not in the GLB files.

## Tests and CI

`python -m unittest discover -s tests -t .` runs the unit tests (axis conversion of the moving parts, the manifest builder, the catalog's type and tag rules) and the site checks; `python tools/check_site.py` checks that every manifest entry has its GLB and thumbnail, that fields are valid and ids unique, and that every moving part names a node that exists in its GLB at the right pivot. `.github/workflows/tests.yml` runs both on every pull request, on every push to `main` and by hand (the repository is public, so Actions on the standard runners are free). A proposal for a Blender job (rebuild a few generators, fail on floating parts or a triangle regression) and for a browser smoke test is in [docs/ci.md](docs/ci.md).
